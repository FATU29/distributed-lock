Pillar 1

Logging — Pino via nestjs-pino

What It Does

  • pino v10 integrated through nestjs-pino v4
  • JSON output in production; pino-pretty in dev (NODE_ENV toggle)
  • X-Request-Id honoured or generated; echoed in response header
  • Every log stamped with trace_id and span_id via pino mixin
  • authorization, cookie, set-cookie headers redacted

Key Interview Points

Q: Why pino over Winston?
~5× faster. With a 200ms p99 budget, 5-10ms lost to logging is unacceptable. Pino serializes JSON without string templates and offloads transport to a worker thread.
Q: Why not console.log?
No level filtering, no structured output, no async sink, no redaction, blocks event loop on stderr writes.
Q: Why nestjs-pino specifically?
Replaces NestJS built-in Logger so framework-internal logs flow through same pipeline. Ties HTTP request logger to AsyncLocalStorage — any service injected gets req.id, trace_id, span_id automatically.

Deliberate Non-Decisions

❌ No log aggregator chosen — emit JSON to stdout, let container runtime handle it
❌ No console.log allowed — ESLint no-console rule enforces this
❌ No in-process pino transports — decouples app failure modes from log pipeline

Key Interview Points

Q: Why Prometheus pull model over StatsD push?
N stateless instances expose /metrics; Prometheus discovers them. Push-based needs sender to know the destination = operational drag. Also, StatsD timer percentiles are per-instance and can't be aggregated — averaging p99s is a textbook anti-pattern.
Q: Why custom histogram buckets?
Default log-scale buckets produce noisy quantile estimates near specific SLO targets. SLO-shaped buckets cost a few extra time-series but pay for themselves in dashboard usability.
Q: Why no business metrics?
Cardinality discipline. "Bookings per dealership per hour" needs dealership labels → cardinality explosion. That belongs downstream of Kafka's appointment.events topic in the analytics consumer.

PromQL Examples

# p99 booking latency (the headline SLO)
histogram_quantile(0.99,
  rate(booking_confirm_duration_seconds_bucket[5m])
)

# Cache hit ratio
sum(rate(availability_cache_outcome_total
  {outcome="hit"}[5m]))
/
sum(rate(availability_cache_outcome_total[5m]))

# Redlock quorum failure rate
rate(redlock_outcome_total
  {outcome="quorum_failed"}[5m])
Pillar 3

Tracing — OpenTelemetry

Setup

  • @opentelemetry/sdk-node + auto-instrumentations-node
  • Exporter: exporter-trace-otlp-http over OTLP/HTTP
  • Bootstrapped in tracing.ts — first import in main.ts
  • Auto-patches: Express, HTTP, ioredis, pg, dns, net, undici
  • fs instrumentation explicitly disabled (noise)
  • SIGTERM handler flushes SDK before exit

Why OTel First Import?

Auto-instrumentations patch modules at require() time. The SDK must start before NestJS / Express / pg / ioredis are loaded, otherwise those modules won't be traced.

Key Interview Points

Q: Why OTel over Jaeger/Zipkin client?
Vendor-neutral wire format (OTLP). Swap Jaeger for Tempo or Datadog without touching app code. Jaeger/Zipkin clients are in maintenance mode.
Q: Why OTLP/HTTP not gRPC?
Firewall-friendly, same port semantics as any HTTP call. Slightly higher overhead than gRPC but exports happen async off the request thread — doesn't matter.

Why Grafana + Loki + Tempo + Prometheus?

  • OSS-first — matches PG, Redis, Kafka posture
  • Unified correlation — click from metric → trace → log in one UI
  • No vendor lock-in — swap any backend (Mimir, VictoriaMetrics, Datadog) without app changes
  • Cost-effective — Loki indexes labels only (not full text), Tempo uses object storage
  • trace_id link — Grafana natively joins Loki logs ↔ Tempo traces via trace_id field

Interview: "Why not Datadog / ELK / CloudWatch?"

Q: Why not just use Datadog for everything?
Datadog hides cardinality cost in the bill — teams ship customer_id as a tag and discover it at month-end. Prometheus makes high-cardinality labels expensive (RAM), forcing the discipline we already want. Also, the app emits vendor-neutral formats (OTLP, Prometheus metrics, JSON logs) — Datadog can consume all of these via an OTel collector if the org mandates it later, without changing app code.
Q: Why not ELK (Elasticsearch + Logstash + Kibana)?
ELK indexes full log content — expensive at scale. Loki indexes only labels (like Prometheus for logs), which is drastically cheaper. For a service emitting structured JSON, label-based queries cover 95% of use cases. And Grafana already visualizes metrics+traces; adding Kibana means two dashboards.
